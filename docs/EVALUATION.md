# Evaluation report

All numbers below were **measured** by `backend/evaluation/run_eval.py` on 30 Oct 2026, on a Windows laptop (Docker Desktop VM with about 7.4 GB RAM, 2 workers). Raw per-document results are in `docs/eval/results-*.json` and per-run summaries in `docs/eval/summary-*.md`. Nothing is estimated.

## Method

- **Dataset:** 108 synthetic documents generated by `tools/datagen` with exact ground truth, plus a 1,000-page PDF holding 411 invoices. The **test** split (46 documents) uses layouts and suppliers that never appear in **dev**: the rules were tuned on dev only, so test numbers are held-out.
  - Digital PDFs in 6 invoice layouts, plus receipts in 2 layouts (thermal slip in dev, retail in test)
  - Scans as image-only PDF, JPG, PNG and multi-frame TIFF, at three degradation levels (good: 300 DPI, ≤0.8° skew; fair: 200 DPI, ≤2.5°, blur, noise; poor: 150 DPI, ≤4.5°, blur, heavy noise, faded)
  - XLSX (junk sheets, header on row 4), CSV (comma UTF-8; semicolon latin-1 with European numbers), and legacy XLS ledgers for PDF-vs-Excel cross-checks
  - Seeded errors: wrong total, line items ≠ subtotal, negative amount, invalid date, exact duplicate, near-duplicate (supplier typo)
  - Failure files: truncated PDF, password PDF, empty file, .docx, text renamed to .pdf, 1,600-page PDF, truncated PNG, corrupt XLSX, blank scan
  - A prompt-injection invoice, invoices missing customer or tax, and bare-"$" invoices
- **Procedure:** empty the database, upload every file of the split through `POST /api/documents` (batches of 20, in manifest order), let the background workers process everything, then read the results back through the API and compare them with the labels.
- **Field accuracy:** exact match after light normalisation (case and whitespace for text, 2-decimal `Decimal` for money, ISO date). A field that is null in the label must also be null. 8 fields per invoice: number, date, supplier, customer, subtotal, tax, total, currency.
- **Timing:** the sum of stage durations from `processing_events` (parse + extract + validate + index), per document and per page. Queue waiting time is excluded; "wall time" covers the whole batch.

## 0. Real-world invoices (read this first)

Synthetic data is good for coverage and regression testing, but it flatters a system tuned on it. So the system is also measured on **real invoices it was never tuned on**, labelled by hand:
- 15 public documents (`data/public/`, from the MIT-licensed invoice2data project): AWS, Odoo, Flipkart, Netpresse (FR), QualityHosting (DE, 2 pages), Coolblue ×2 (NL), Free (FR), OYO receipt (IN), Saeco (NL), Sammy Maystone, plus 4 PNG renderings.
- 2 of the owner's own invoices (`data/real/`, private, not in git): a 497×706 px PNG screenshot of an Intercloud invoice, and a 2-page Shopify bill.

| Field accuracy | Original pipeline (30 Oct) | Rules only, now | **Rules + Gemma (text + vision), now** |
|---|---|---|---|
| 15 public invoices | 45.8% | 70.0% | **86.7%** |
| 2 owner invoices | 37.5% | 50.0% | **93.8%** |
| Synthetic digital PDFs (for comparison) | 98.1% | 98.4% | — |

Per field on the public set with the LLM: invoice number 86.7%, date 100%, supplier 53.3%, customer 66.7%, subtotal 73.3%, tax 100%, total 93.3%, currency 86.7% (from the first full LLM run; the final run's per-field table is in `docs/eval/summary-public-llm.md`).

What changed between the columns (DECISIONS 22–27):
1. PDF text is rebuilt in visual row order. Real PDFs often store a value before its label.
2. General rules for real layouts: Dutch/French labels, "Bill to Address / ATTN:", "Service Provider", "Account billed", issuers in footers, VAT/TIN numbers no longer read as amounts.
3. When the LLM is called, it is asked for every weak field, not only the required ones. It is also called when 3+ fields are weak.
4. **Vision fallback.** For a poor scan, Gemma reads the page image. On the 497 px screenshot, OCR could not read a single amount; vision read 7 of 8 fields correctly. The 8th was the supplier, given as "InterCloud" instead of "InterCloud Limited". These values are marked for a person to confirm.
5. Bugs found by measuring:
   - fake LLM answers had been cached and reused by real runs
   - grounding matched inside words ("Total" inside "Subtotal")

Notes on cost and latency:
- On real-world documents the LLM is needed far more often: 14 of 15 public invoices and both owner invoices called it, against 17–25% on synthetic data.
- The free tier answered in 20–120 s per call. The first uncached run over the 15 public documents took 661 s end to end; reruns hit the cache.
- Remaining misses are mostly party names: who is the supplier on an Odoo template, "OYO" vs its legal entity "Oravel Stays", an issuer printed only inside an image.
- With 17 documents, one document moves the result by about 6 points; treat these as indicative.

How to read this:
- **Validation does what it should.** Every seeded error type (wrong total, lines ≠ subtotal, negative amount, invalid date, exact duplicate, near-duplicate with a supplier typo, bare "$") is caught on digital documents. No clean document with correct extraction is ever flagged. The two seeded documents missed across all data are scans of the bare-"$" supplier: OCR misread the "$", so the ambiguity never reached validation.
- **Clean documents that went to review** are all scans (plus one scanned receipt) where OCR misread a number, so subtotal + tax ≠ total. Sending them to a person is the intended behaviour, but it costs reviewer time.
- **Cross-check misses** all come from wrongly extracted dates (below), not from the matching logic: the right row is found, but the date differs.

## 4. Known weak spots (honest list)

1. **Poor-quality scans** (150 DPI, 4–5° skew, heavy noise, faded): 40% field accuracy rules-only, 56% with the LLM. Good and fair scans are about 90%. Better OCR (a stronger engine, or a vision model) is the next step; Tesseract was kept for its small footprint.
2. **Ambiguous dates** like 04/12/2026 on non-US suppliers using US-style dates: one test layout prints MM/DD/YYYY for UK, Italian and Indian suppliers, and the system reads them day-first. This one cause explains most invoice-date misses and all remaining cross-check misses. These values are marked lower confidence (0.75) but not flagged as errors.
3. **LLM latency and reliability on the free tier:** usable as a fallback for about 1 invoice in 6, not as the main path.
4. **Synthetic data:** generated invoices are cleaner and more regular than real ones. `data/real/` is prepared for 10–25 public invoices with hand-written labels; that has not been done yet.
5. **Line items** are extracted and used for checks, but they are not part of the scored field accuracy.

## Reproduce

```powershell
docker compose up -d --build
docker compose exec api python -m evaluation.run_eval --split test --reset --name test-fake
docker compose exec api python -m evaluation.run_eval --split all --reset --large --name all-large
# real LLM (needs GEMINI_API_KEY in .env; uses free-tier quota)
$env:LLM_FAKE="false"; docker compose up -d worker
docker compose exec -e LLM_FAKE=false api python -m evaluation.run_eval --split test --reset --name test-real-llm
```
